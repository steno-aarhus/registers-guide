OSDC - Open Source Diabetes Classifier

Find the people with type 1 or type 2 diabetes in the Danish registers, with an inclusion date, using the osdc R package

OSDC finds the people in the Danish registers with type 1 or type 2 diabetes from BEF, LPR, LMDB, the health insurance registers and lab data. Run the osdc R package, or use a pre-computed population if your project has one.
Last modified

November 23, 2026

Use this page when diabetes is part of your study: as an exposure, an inclusion or exclusion criterion, or a covariate, and especially when you need to tell type 1 from type 2 diabetes, which diagnosis codes in LPR (the National Patient Register) alone do not do reliably. OSDC is an open source algorithm, published as the R package osdc, that classifies diabetes from diagnoses, prescriptions, podiatrist services and HbA1c results. You need access to five registers (listed below). You end with one row per person with diabetes, their type and the date they enter the diabetes population.

Article: doi:10.2147/CLEP.S407019 Documentation and code: steno-aarhus.github.io/osdc

The package README says that minor changes have been made to the algorithm since the validated version in the article, and that more are expected; the changes are listed in the repository.

What OSDC gives you

classify_diabetes() returns one row per person classified as having diabetes, with five columns. People without diabetes are not in the output: “no diabetes” means “not in the table”.

Column Contents
pnr Personal identifier
raw_inclusion_date The date of the person’s second inclusion event (inclusion requires two)
stable_inclusion_date The same date, but NA if it falls before 1 January 1998
has_t1d TRUE/FALSE: type 1 diabetes
has_t2d TRUE/FALSE, defined as !has_t1d, so the two are complements

The inclusion events are HbA1c of 48 mmol/mol or more, a hospital diagnosis of diabetes, a diabetes-specific podiatrist service and a purchase of glucose-lowering drugs. The dates are inclusion dates, the date a person enters the diabetes population, not a date of disease onset, and there is no age at onset.

Choosing between the two dates is a study decision. Before 1998 the register data may not be good enough to tell new (incident) cases from existing (prevalent) ones, so stable_inclusion_date is blank for inclusions before then. The 1998 default is one year after pregnancy data in LPR became usable for dropping purchases related to gestational diabetes. Filter on stable_inclusion_date and every case included before 1998 leaves your cohort without an error. Use raw_inclusion_date and you keep them, at the cost of dates the package’s authors flag as uncertain. Decide which, and say which in your methods section. The cutoff is an argument, stable_inclusion_start_date, if your LPR and LMDB data start later than 1997.

Run osdc on your project

osdc is on CRAN. Install it, then load it:

install.packages("osdc")
library("osdc")

install.packages() installs dependencies that are missing, but it does not update ones that are already installed; R’s own help advises running update.packages() first. The pre-installed packages on DST may be old, so if library("osdc") stops with a version error, update the package it names.

classify_diabetes() takes one argument per register (lpr, hsr, lab_forsker, bef, lmdb). Each must be a DuckDB table covering all the years you have, for example a connection to your parquet files. LPR must first be combined into one table, and so must the two health insurance registers, with join_registers(). The getting-started guide, steno-aarhus.github.io/osdc/articles/osdc.html, walks through this step by step.

Is osdc available on your project? It is confirmed on DARTER (project 708421). It is likely available on other projects too, but this has not been verified. Check with "osdc" %in% rownames(available.packages()) on your own server (the package is not pre-installed, so available.packages() shows whether it can be installed). If it is missing, you can ask DST to install it.

The registers osdc needs

classify_diabetes() uses BEF, LPR, LMDB, the health insurance registers (sysi/sssy) and laboratory results, and needs all five: it has one argument for each (osdc design vignette).

Missing one of the five? Two different reasons, two different fixes:

  • sysi/sssy: these are ordinary DST registers. If they are missing, your project has not requested them; ask for them to be added.
  • Laboratory results: these are not a DST register. They come from the Danish Health Data Authority (Sundhedsdatastyrelsen) through a separate Forskerservice application, so they never appear in DST’s own overview. See Laboratory results for the table names and how the data are reached.
NoteWhich glucose-lowering drugs count as inclusion events?

Not every purchase of a glucose-lowering drug (ATC A10) counts:

  • All GLP-1 receptor agonists (GLP-1 is glucagon-like peptide-1) are dropped, because this drug class is used extensively for weight loss in people without diabetes.
  • Dapagliflozin and empagliflozin, two SGLT-2 inhibitors (sodium-glucose co-transporter 2), are dropped when bought on their own, because Danish guidelines recommend them for heart and kidney failure in people without diabetes.
  • Combination drugs with a GLP-1 receptor agonist or an SGLT-2 inhibitor together with another glucose-lowering drug do count.
  • Purchases during pregnancy are dropped, and so is metformin bought by women under 40 or with a polycystic ovary syndrome indication code.

The exact logic is in the algorithm vignette and the code on GitHub.

The type is decided with data from after your index date

Run on all years, the type classification uses information from after your index date. Type 1 versus type 2 is decided from the person’s whole record: the share of diagnoses that are type 1, and insulin purchase patterns. A person’s type can therefore depend on events that had not happened on your index date. If you use the type as a baseline variable, you classify people with information from the future (look-ahead misclassification). This applies to a pre-computed population too, since it is run on all years.

To avoid it, run classify_diabetes() yourself on register data filtered to before your index date, so the classification only sees pre-index information. If you change the algorithm itself, for example to count GLP-1 receptor agonists, the published validation no longer applies.

On DARTER: a pre-computed population

NoteDARTER (project 708421): where the pre-computed files are, and the old population

On DARTER the OSDC classification is already computed, so you do not need to run the algorithm yourself unless the look-ahead problem above matters for your study. The path and the name osdc (and read_register("osdc")) are DARTER-specific; on other projects the file is named differently and lives elsewhere.

The 2024 population was generated, on the latest data, after the package was updated and released on CRAN. It is valid for inclusions until the end of 2024 and replaces the previous population file: use one or the other, never both. The previous files are kept for reproducibility.

  • Parquet: E:/workdata/708421/cleaned-data/parquet-external/osdc/2024, which read_register("osdc") finds on DARTER
  • .csv, .rds or .dta: E:/workdata/708421/cleaned-data/diabetes_register_pop/2024
library(fastreg) # read_register()
dm_pop <- read_register("osdc") # the 2024 population; DARTER only

The previous population (up to 2022), for reproducibility only. It has a different output format; the column names below apply only to the old file.

library(dplyr) # rename, filter, select

dm_pop <- readRDS("E:/workdata/708421/cleaned-data/diabetes-register-pop/dm_population_1977_2022.rds")

names(dm_pop)
# [1] "PNR"           "diabetes_type"  "do_dm"          "age_at_onset"

dm_pop <- dm_pop %>% rename(pnr = PNR) # lower-case pnr, as everywhere else

# diabetes_type: 1 = T1D, 2 = T2D  |  do_dm: the date in the old file

t1d <- dm_pop %>%
  filter(diabetes_type == 1) %>% # type 1 only
  select(pnr, diabetes_type, do_dm) %>%
  rename(date_diabetes = do_dm)
