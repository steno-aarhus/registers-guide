Socioeconomic variables

Education, income and employment following the SEPLINE approach

Published

September 24, 2026

You now know the pattern: read_register/open_dataset → filter → collect → left_join. That is exactly what you use here. Two things are new in this phase:

  1. “Fetch for the year before index date”: SES registers are annual snapshots. You cannot just filter on pnr; you must also match on which year is relevant per person (year(index_date) - 1). This is done by calculating the baseline year per person and using it as a join key.
  2. FAIK via familie_id: Income is linked to the household, not the person directly. You need BEF as a bridge: fetch familie_id from BEF for the baseline year, then join to FAIK on familie_id.

The rest is categorisation per SEPLINE guidelines.

What SEPLINE is, and what this page covers

Socioeconomic position (SEP) is a latent construct - it cannot be measured directly, only approximated through proxies. Many variables can serve as that proxy (education, income, occupation, wealth, housing, area-level deprivation, and more), and studies have historically picked different ones, measured them at different times relative to their exposure, and categorised them differently - which makes results hard to compare across studies. SEPLINE is a 2025 Danish national guideline written to fix exactly that: a consensus document, developed through two workshops with researchers, universities and data holders across Denmark, recommending which register variables to use for SEP, when in a study to measure them, and how to categorise them, so that studies using Danish registers report comparable things when they say “adjusted for socioeconomic position.”

SEPLINE article: Hjorth et al. Clinical Epidemiology 2025 - doi:10.2147/CLEP.S520772, with a corrigendum (Hjorth et al. 2026) correcting two of its tables. See the article for full justification, recommended reference groups and categorisations.

SEPLINE covers four SEP dimensions, not three - this page implements three of them. Directly from the article: “This guideline encompasses educational level, labor market affiliation or occupation, income, and wealth, alongside closely related sociodemographic factors such as marital or cohabitation status, ethnicity, and area-level characteristics.” Wealth is a co-equal fourth SEP dimension in SEPLINE’s own definition, not covered on this page yet (Table 7’s FGNF_2020/FAMFORMREST_NY05 are not built out here - get in touch if you have working code for it). Marital or cohabitation status is explicitly not SEP in SEPLINE’s own framing - it is a related sociodemographic factor, recommended alongside SEP for a fuller picture, not as part of it. Its own note: cohabiting or married people tend to have better health outcomes and lower mortality, but “though not a traditional indicator of socio-economic position,” including it helps identify vulnerable groups that SEP alone misses. SEPLINE’s own default for Denmark is cohabitation status, not marital status - many Danish couples live together unmarried, so marital status alone misses them; marital status is suggested only as a supplementary analysis, mainly for international comparability. Neither is implemented on this page.

SEPLINE gives you separate indicators, not one combined score. Unlike, say, NMI, which deliberately produces one weighted number, SEPLINE stops at the individual-indicator level and says so directly: “For some settings, it may be meaningful to combine these individual indicators into a composite measure or socioeconomic index to reflect the multidimensional nature of socioeconomic position, however, such approaches are not addressed in this guideline.” Expect education_cat, occupation_cat and income_cat as three separate covariates at the end of this page, not one SEP score - a composite index is a decision and a method you (or your analysis plan) would need to justify independently; SEPLINE does not hand you one.

ImportantStructural guidance, not verified code

The categorisations below are not validated. They show how to code the variables, not an approved implementation, so review them against your own analysis plan before you use them. Have working code, or input on the categorisations? Get in touch.

The examples read registers by name with read_register(), which assumes fastreg is pointed at your registers. Without fastreg, use open_dataset("path/to/akm/") instead. Column names differ between deliveries, so check yours with names(your_data).

Fetch the variable for the year BEFORE index by default - but SEPLINE does not use one timing rule for all three dimensions. All three registers are annual: each person has one value per calendar year. If you take the value from the index year itself, you risk measuring status that falls after your exposure. Example: index = surgery date 15 June 2015. The 2015 value may reflect status after the surgery and be affected by the exposure itself (e.g. job loss after illness) - that gives reverse causation, whereas you want a baseline value from before the exposure.

year(index_date) - 1 is a safe default, and this page uses it throughout for consistency. But SEPLINE’s own tables set the timing per dimension, not once for all three:

  • Income (Table 8): strictly the three years preceding the index year, never the index year itself - no ambiguity here, see the income section below.
  • Employment (Table 5): “the latest available status at index date,” in practice the year before index for AKM’s annual snapshot. SEPLINE’s own caveat: go earlier still if your specific outcome carries a strong reverse-causation risk, or use DREAM instead of AKM if you need closer-to-index granularity (DREAM updates weekly, not annually).
  • Education (Table 2): “the latest available educational level at index date” - not the year before. A completed degree cannot be undone by illness, so education does not carry the same reverse-causation risk as employment or income. See the education section’s own callout for how to follow this looser rule instead of the page’s default.

So year(index_date) - 1 is this page’s uniform default, not SEPLINE’s uniform rule - know the difference before you defend the choice in a methods section.

The three dimensions on this page

Dimension Register Variable
Education UDDA hfaudd - highest completed education (DISCED-15 code)
Income FAIK famaekvivadisp_13 - household-equivalised disposable income
Employment AKM socio13 - labour market classification

Wealth is SEPLINE’s fourth SEP dimension and is not in this table - see above for why. SEPLINE specifies both how each of the three variables here is categorised and when in the follow-up it is measured.

Before you extract anything: give the cohort a stable row id

This page joins on row_id, not pnr, throughout. If your cohort has exactly one row per person, that makes no difference to you - skip ahead. If it does not (e.g. a comparison group matched with replacement, see comparison cohort’s note on it), row_id is what keeps a repeated pnr’s different index_dates from getting mixed up in the joins below - with no error and no NA to flag it if it went wrong.

library(dplyr) # mutate, left_join, group_by, summarise, bind_rows
library(lubridate) # year() to extract year from a date

cohort <- cohort %>%
  mutate(
    row_id = row_number(), # one id per cohort row - stays unique even if pnr repeats
    year_baseline = lubridate::year(index_date) - 1 # baseline year, computed once and reused below
  )

Every join from here on uses row_id (to attach a finished variable back onto cohort) or pnr + year_baseline together (to pull a value out of a register) - never pnr by itself.

A collect()ed register extract only contains rows that matched your filter. Someone with zero qualifying records - no UDDA row before their baseline year, no AKM row for their exact baseline year, no household match in BEF - is simply absent from that table, not present with an NA. Left-join such a table onto your cohort and those people get NA for the derived variable.

That matters more than it looks. Most R modelling functions, including survival::coxph(), drop any row with an NA covariate by default (na.action = na.omit) - silently, with no warning. A person with unknown education does not become an “Unknown” category in your model, they vanish from the analysis entirely, and your model’s N no longer matches your cohort’s N.

The fix used throughout this page: join onto the full cohort (via row_id) before you categorise, not after. Then case_when(... TRUE ~ "Unknown") catches the NA and turns it into an explicit category, the same way it already catches any other unmatched code. The stopifnot(nrow(...) == nrow(cohort)) checks in the code below exist to confirm this: as long as row counts hold at every step, nobody has been silently dropped. Before you trust a downstream model, also check its N against your cohort’s N directly - this exact pattern (register extract → collect → categorise → model) is not specific to SES variables, so the same check is worth applying anywhere else in your pipeline that joins a register onto a cohort and feeds the result into a regression.

Employment - AKM (socio13)

socio13 is DST’s socioeconomic classification. The full code list, with what each value means, is in DST’s classification documentation: SOCIO →.

DST’s words are narrower than the everyday ones. “Beskæftiget” is a statistical definition with thresholds attached, not simply “has a job”, and the same goes for “husstand” and “disponibel indkomst” further down this page. If you are about to write in a methods section what a category means, look the word up first: Hvad betyder →. Getting this wrong does not produce an error, it produces a sentence in your paper that does not match your data.

One code is easy to get wrong. 420 is children under 15, a real category rather than a missing value, so seeing it in an adult cohort means the index date is wrong, not that the data is incomplete.

410 (“Andre” in DST’s own SOCIO nomenclature) is grouped with Unemployed here, per SEPLINE’s corrected Table 6 - this was genuinely ambiguous until a 2026 corrigendum fixed it. The original article’s Table 6 listed 410 in two rows at once: under “B1: Unemployed (210, 410)” and under “Missing/other”. The corrigendum (Hjorth et al. 2026) corrects Table 6 and removes 410 from “Missing/other,” leaving it only under B1 Unemployed - so the code above follows the corrected table, not the ambiguous original. DST’s own code list still calls 410 “Andre” as its own nomenclature category; SEPLINE’s corrected categorization for analysis groups it with Unemployed regardless.

AKM has a documented gap in 2014. SEPLINE’s Table 4 (Data Sources for Labor Market Affiliation) states, without further detail: “Data gap in 2014.” Nothing elsewhere in the article says what the gap actually is - a missing year entirely, partial coverage, or specific codes affected - so check your own extract before trusting any 2014 socio13 value:

akm %>% filter(year == 2014) %>% count(socio13) %>% collect()

Compare the total row count and code distribution against a neighbouring year. If your cohort has baseline years in 2014, resolve this before you trust that year’s employment status.

Two things about year before you join on it. It is not a DST variable - it comes from the parquet partitioning, so confirm the name in your own files (Phase 4). And do not assign to it: mutate(year = ...) overwrites the partition column rather than adding one, which silently breaks every join in this chapter, since they all join on person plus year. Give a derived year its own name, e.g. index_year.

library(fastreg) # read_register() - reads registers by name
library(arrow) # open_dataset() - fallback without fastreg

# 1. Open AKM via fastreg (read_register gets the path from your project config)
akm <- read_register("akm") %>%
  rename_with(tolower) # standardise column names
# Without fastreg: open_dataset("E:/workdata/[projectnumber]/cleaned-data/parquet-registers/akm/") %>% rename_with(tolower)

# 2. Fetch employment status for every baseline year the cohort needs.
# unique() here is only an efficiency filter: cohort$year_baseline has one
# value PER ROW (with repeats - many people share a baseline year), and
# unique() collapses that to the distinct set of years so the query below
# does not re-read a year twice. It does NOT pair a year back to a person -
# that pairing happens in step 3, via the join, using pnr + year_baseline
# together.
index_year <- unique(cohort$year_baseline)

# copy = TRUE: akm is a remote/database connection (fastreg may route through
# DuckDB), tibble(pnr = ...) is a local R object. dplyr will not silently join
# across two different sources - copy = TRUE is your explicit permission to
# copy the small local pnr list into the database so the join can run there.
# Without it the join errors outright (it does not affect correctness, only
# whether the code runs at all) - needed on every semi_join in this pattern,
# not just this one, e.g. also for LPR extracts.
akm_data <- akm %>%
  semi_join(tibble(pnr = cohort$pnr), by = "pnr", copy = TRUE) %>% # only the cohort's pnr's
  filter(year %in% !!index_year) %>% # only years the cohort actually needs
  select(pnr, year, socio13) %>% # only the columns we use
  collect() # fetch into R

# 3. Attach to cohort - one row per cohort row, matched to THAT row's own
# baseline year (year_baseline already exists on cohort, see "Before you
# extract anything" above)
cohort_akm <- cohort %>%
  left_join(akm_data, by = c("pnr", "year_baseline" = "year")) # pnr + year together, not pnr alone

# Sanity check: a correct join never changes the row count
stopifnot(nrow(cohort_akm) == nrow(cohort))

# 4. Categorise per SEPLINE
cohort_akm <- cohort_akm %>%
  mutate(
    occupation_cat = case_when(
      socio13 %in%
        c(
          110,
          111,
          112,
          113,
          114,
          120,
          131,
          132,
          133,
          134,
          135,
          139
        ) ~ "Employed",
      socio13 == 310 ~ "Student", # under uddannelse
      # 210 arbejdsløse mindst halvdelen af året, 410 "Andre" - SEPLINE Table 6
      # groups both under B1 Unemployed (corrigendum-corrected version, see below)
      socio13 %in% c(210, 410) ~ "Unemployed",
      # 220 sygedagpenge/orlov, 321 førtidspension, 330 kontanthjælp
      socio13 %in% c(220, 321, 330) ~ "Outside labour market",
      socio13 %in% c(322, 323) ~ "Retired", # folkepension, efterløn
      socio13 == 420 ~ "Child under 15", # should not occur in an adult cohort
      TRUE ~ "Unknown" # missing
    )
  )
WarningCheck your AKM before you trust this join

The recipe above assumes one row per pnr per year in akm_data - that is why the join on pnr + year_baseline does not need a dedup step. SEPLINE’s own description of socio13 backs this up: “employed individuals are registered based on their main occupation during a given year, based on the activity that generated the largest amount of income” (Hjorth et al. 2025, doi:10.2147/CLEP.S520772, Table 6, Labor Market Affiliation). DST resolves multiple jobs to one code before the register is delivered, so a standard AKM delivery should not have duplicates.

SEPLINE later published a corrigendum (Hjorth et al. 2026) to that same Table 6: it adds DREAM codes for people awaiting a flex job (740, 743–748) that the original table missed, merges the old Senior Pension code into C3 Disability Pension (noting that Statistics Denmark confirmed both schemes fall under socio13 code 321), and - relevant to step 4 above - removes 410 from “Missing/other,” leaving it only under B1 Unemployed (see the callout further up this section). It does not touch the main-occupation rule quoted above, and says nothing about handling multiple jobs or codes within a year - so do not lean on the corrigendum for that question, it fixes a different part of the table.

Whether your delivery matches this depends on your data, so check rather than assume:

akm_data %>%
  count(pnr, year) %>%
  filter(n > 1)

If this is empty: socio13 is already the dominant occupation, nothing further needed.

If it is not empty: first drop exact duplicates - same pnr, year and socio13 repeated:

akm_data <- akm_data %>%
  distinct(pnr, year, socio13) # one row per person per year

Re-run the count above. Rows that still differ in socio13 for the same person-year are not something SEPLINE or DST resolves for you: the corrigendum patches a different part of Table 6, not this. If you still need one row per person-year, pick a tie-break priority order and document it, rather than choosing silently - e.g. ranked by attachment to the labour market, using the occupation_cat grouping from step 4 above (not raw socio13, which is a code list, not a scale):

Employed > Student > Unemployed > Outside labour market > Retired > Unknown

This ordering is our own convention, not SEPLINE’s - review it against your own analysis plan before using it.

Education - UDDA (hfaudd)

hfaudd is short for højest fuldførte AUDD - the highest completed education, coded with an AUDD code. It is a four-digit DISCED-15 code for the specific education a person completed: 4112 is “electrician”. It is an identifier, not a scale, so the level (short / medium / long) has to be looked up, not read off the digits. UDDA itself does not carry the level.

The AUDD in the name matters when you go looking for a lookup table: DISCED-15 codes come in two flavours, AUDD for a completed education and UDD for one that is ongoing or was interrupted. DST documents them as two separate classifications, DISCED-15 AUDD and DISCED-15 UDD. hfaudd is completed, so it is an audd lookup you want.

Do not derive the level from substr(hfaudd, 1, 2). The level codes (10, 15, 20, 30, 40, 70, 90) look just like the first two digits of an education code, so it is the obvious thing to try - and it is wrong roughly 4 times in 10, silently. You need the lookup. Why it fails is set out in Overview of registers.

# 1. Open UDDA via fastreg (read_register gets the path from your project config)
udda <- read_register("udda") %>%
  rename_with(tolower) # standardise column names
# Without fastreg: open_dataset("E:/workdata/[projectnumber]/cleaned-data/parquet-registers/udda/") %>% rename_with(tolower)

# 2. Fetch every education record up to the latest baseline year anyone in the
# cohort needs (broader than AKM/FAIK's exact-year filter on purpose - step 3
# below needs each row's history, not just its one exact baseline year).
udda_data <- udda %>%
  semi_join(tibble(pnr = cohort$pnr), by = "pnr", copy = TRUE) %>% # only the cohort's pnr's, copy = TRUE: see AKM step 2
  filter(year <= max(cohort$year_baseline)) %>% # every year any row could fall back to
  select(pnr, year, hfaudd) %>% # only the columns we use
  collect() # fetch into R

stopifnot(nrow(udda_data) > 0)

# 3. For each cohort row, keep its OWN most recent record at or before ITS
# baseline year - not a global "newest year fetched" (the earlier version of
# this page did that with group_by(pnr) %>% slice(1), which silently hands a
# later row's education to an earlier row once the same pnr repeats with two
# different baseline years - see "Before you extract anything" above). This
# also means a gap in the exact baseline year no longer becomes a missing
# value: the most recent earlier record carries forward, since a completed
# education does not regress. left_join (not inner_join) keeps rows for
# people with zero UDDA records too, as NA - see the NA-vs-Unknown callout
# above for why that matters.
cohort_udda <- cohort %>%
  select(row_id, pnr, year_baseline) %>%
  left_join(udda_data, by = "pnr", relationship = "many-to-many") %>% # every row x every record for that pnr, on purpose
  filter(is.na(year) | year <= year_baseline) %>% # only records at or before this row's own baseline
  group_by(row_id) %>%
  slice_max(year, n = 1, with_ties = FALSE) %>% # this row's own most recent record
  ungroup()

stopifnot(nrow(cohort_udda) == nrow(cohort))

# 4. Look the level up - one row per education code, joined on hfaudd
library(heaven) # edu_code: 4,621 DISCED-15 codes with their level
data(edu_code)

cohort_udda <- cohort_udda %>%
  mutate(hfaudd = as.character(hfaudd)) %>% # match the type in edu_code
  left_join(
    edu_code %>%
      as_tibble() %>% # edu_code is a data.table
      mutate(hfaudd = as.character(hfaudd)) %>%
      select(hfaudd, level_code = number), # number = the two-digit level
    by = "hfaudd"
  )

# 5. Group the level into the SEPLINE categories
cohort_udda <- cohort_udda %>%
  mutate(
    level_code = as.numeric(level_code),
    education_cat = case_when(
      level_code %in% c(5, 10, 15) ~ "Short", # pre-school, primary, preparatory
      level_code %in% c(20, 25, 29, 30, 35, 39) ~ "Medium", # upper secondary and vocational
      level_code >= 40 & level_code < 90 ~ "Long", # short cycle higher and above
      TRUE ~ "Unknown" # 90 "not stated", no UDDA record at all, or no match in edu_code
    )
  )

# ALWAYS check how many did not match - a high number means a type mismatch
# on hfaudd, or codes that are not in the lookup.
cohort_udda %>%
  summarise(unmatched = sum(is.na(level_code)), total = n())

SEPLINE actually allows a looser cutoff than this code uses. Table 2 of the article times education at “the latest available educational level at index date” - not the year before, unlike employment and income. The reasoning is specific to education: a completed degree cannot be undone by your exposure, so there is no reverse-causation risk to guard against by stepping back a year. This code still uses year_baseline (before index) to stay consistent with the rest of the page and err conservative. If you want to follow SEPLINE’s literal rule, replace year_baseline with lubridate::year(index_date) in step 3’s filter (and fetch one more year in step 2) to allow records from the index year itself.

Getting heaven outside DST. On DST it is already installed, which matters because the server has no internet - you could not install it there yourself. Elsewhere it is not on CRAN, so install.packages("heaven") will not find it, but it installs from GitHub in one line:

# install.packages("pak")
pak::pak("tagteam/heaven")

If you would rather not add the dependency, DST has the same lookup on the server. The level files live in SAS_datasaet/Uddannelser/ and are named by the levels they map between: an L1 → L5 file turns the four-digit hfaudd into the Hovedgruppe (10 Grundskole, 20 Gymnasiale, 30 Erhvervsfaglige, … 80 Ph.d.). Format tables has the naming systematics, the code, and the three things to check first.

This DST format-table route, not heaven::edu_code, is what SEPLINE’s own Table 3 actually names. Its corrigendum-corrected version gives the exact format: “Convert HFAUDD to DISCED by using the latest available format (eg, $AUDD2023_HOVED_LIL2_KT). The formats are located at the desktop shortcut ‘DST – Formater’ under ‘Uddannelser (DISCED - Hovedområder med historik)’” (Hjorth et al. 2026, doi:10.2147/CLEP.S612503). This page still uses heaven::edu_code as the worked example - it needs no DST session to test against, which matters for a guide read outside DST - but if you want to cite that your categorization follows SEPLINE’s own specified source rather than a third-party package, this is the route to use, and the $AUDD2023_HOVED_LIL2_KT name (or whatever the current year’s version is called) is worth checking for directly with list.files() before you commit to c_audd2015_l1l5_kt or any other vintage shown here.

Whichever source you use, the shape of the solution is the same: a table of education codes joined to your data on hfaudd. What you must not do is skip the lookup.

Use one lookup for the whole study, and write down which one. DST’s folder holds several versions of the classification side by side (2008, 2011, 2015, possibly newer). You do not need one per study year: DST updates the newest version with older codes as well, so the latest file covers your whole period. Take the newest.

The two routes will not necessarily give you the same set of categories though. heaven::edu_code follows DISCED-15 and splits education into 15 groups; DST’s level-5 Hovedgruppe is a nine-way split. Neither is wrong - they are different levels of detail. Compare them on your own data before you commit, and report which one you used.

The grouping in step 5 is our reading of SEPLINE, not a validated implementation. edu_code gives you the level reliably; how those levels are collapsed into “short / medium / long” is a study-design choice. Check the SEPLINE article for the categorisation your analysis should use, and note that edu_code also carries a ready-made 5-level grouping (code5txt) and ISCED codes (isced_code) if either fits better.

Income - FAIK via BEF (famaekvivadisp_13)

Income is linked to the household, not the person - and that is a deliberate choice, not just a fact about how FAIK is structured. SEPLINE’s Table 7 recommends equivalized disposable household income (famaekvivadisp_13/aekvivadisp_13) as the default, “unless disposable personal income better accommodates the research question” - individual income (perindkialt_13) is a documented, valid alternative for some study designs (e.g. questionnaire-based research benchmarking against a survey population’s own pre-tax income), not simply the wrong choice. This page only implements the household route. You need familie_id from BEF as a bridge. SEPLINE’s actual rule (Table 8, “Data Management of Income and Wealth”): average the three calendar years preceding the year of index (not the index year itself, to avoid reverse causation), then classify into quintiles stratified by sex × 5-year age group × calendar year, computed against the general population - not your own cohort’s distribution. The suggested output is 3 categories, not 5 (Table 9): quintile 1 = Low, quintiles 2-4 = Medium, quintile 5 = High.

famaekvivadisp_13 has a sister column, famaekvivadisp, with no suffix. The _13 one is not simply the newer of the two: DST gives the old column the years 1990-2012 and the _13 column 1987-2024, so the newer definition was applied backwards as well as forwards. Use _13 for the whole period. Splicing the two at 2013 mixes two definitions inside one series.

# 1. Open BEF + FAIK via fastreg (read_register gets the path from your project config)
bef <- read_register("bef") %>%
  rename_with(tolower)
faik <- read_register("faik") %>%
  rename_with(tolower) # check whether FAIK is one row per family in YOUR data - see the callout below
# Without fastreg: open_dataset("E:/workdata/[projectnumber]/cleaned-data/parquet-registers/bef/") %>% rename_with(tolower)  (same for faik)

# 2. Fetch familie_id from BEF for every baseline year the cohort needs (see AKM step 2 for what unique() does)
bef_family <- bef %>%
  semi_join(tibble(pnr = cohort$pnr), by = "pnr", copy = TRUE) %>% # only the cohort's pnr's, copy = TRUE: see AKM step 2
  filter(year %in% !!index_year) %>% # only years the cohort actually needs
  select(pnr, year, familie_id) %>% # familie_id is the bridge to FAIK
  collect() # fetch into R

# 3. Fetch income from FAIK for the same years
faik_data <- faik %>%
  filter(year %in% !!index_year) %>% # only years the cohort actually needs
  select(familie_id, year, famaekvivadisp_13) %>% # only the columns we use
  collect() # fetch into R

# 4. Attach to cohort - one row per cohort row, matched to THAT row's own baseline year
cohort_income <- cohort %>%
  left_join(bef_family, by = c("pnr", "year_baseline" = "year")) %>% # this row's own household, for its own baseline year
  left_join(faik_data, by = c("familie_id", "year_baseline" = "year")) # then that household's income, same year

stopifnot(nrow(cohort_income) == nrow(cohort))

This single-year version is here to show the join shape. SEPLINE’s actual income measure is the 3-year mean below - cohort_income is not what carries through to the final assembly.

WarningCheck your FAIK before you trust this join

The recipe above assumes FAIK holds one row per family per year - that is why the bridge goes through familie_id. On DARTER that stopped being true from 2022 onward: FAIK now also carries pnr, and each family’s row is repeated once per family member. Whether this applies to your project depends on your data delivery, so check rather than assume either way.

names(faik) # is pnr among the columns?

# More than one row per family and year means the duplication applies to you
faik %>%
  count(familie_id, year) %>%
  filter(n > 1) %>%
  count() %>%
  collect()

What it does to the code above. The join on familie_id + year returns one row per family member instead of one per person, so your dataset grows without any error. And the 3-year average further down is then computed over a set weighted by household size: a five-person family counts five times as much as a single person in the same year. The numbers stay plausible throughout, which is what makes it dangerous.

If it applies to you, one line before the join fixes it. Collapse the duplicates back to one row per family-year, and the rest of the recipe works unchanged for every year:

faik <- faik %>%
  distinct(familie_id, year, famaekvivadisp_13) # one row per household per year

If your FAIK carries pnr for all years, you can join income to pnr directly and skip the BEF bridge entirely.

A ready-made alternative: heaven::averageIncome() does the multi-year average in one call, uses only the years strictly before the index year, and keeps one row per person-year - so repeated rows for the same person and year collapse on their own. That happens to cover the FAIK duplication above, though the function was written for a different reason (quarterly duplicates), so do not treat it as a guarantee.

It does not replace the BEF bridge: the income table you hand it must already be linked to pnr. heaven is pre-installed on DST and installs from GitHub elsewhere (pak::pak("tagteam/heaven")), so the choice is about whether you want the dependency - the code below is the version with no packages beyond the ones you already use.

3-year average and quintiles (SEPLINE recommendation)

This is a worked implementation of Table 8’s rule, not a simplified stand-in - see the callouts below for its cost and the choices it still leaves to you.

This works with BEF and FAIK for the whole Danish population, not just your cohort. Steps 5-6 below deliberately drop the pnr filter, because SEPLINE stratifies income quintiles against the general population (Table 8, “Standardization”), not against your own cohort’s distribution - ntile(mean_income, 5) on the cohort alone answers a different question (how your participants rank against each other, not against the population).

RAM: the filtering and averaging stay inside the database, not in R - but this is not yet tested at real scale, and may still be a problem. Steps 5-6 hold off on collect() until after group_by()/summarise(mean(...)) has already run, so what actually reaches R is one row per (person, sex, age-group) - not the raw population x 3-years join, which would be tens of millions of rows. This was checked against a small local, synthetic DuckDB connection (year(), floor(), mean() and the join all confirmed to translate to SQL and run there), not against a real DST session and not at the full Danish population’s actual scale (5.9 million people across several years). Whether it holds up depends on your fastreg setup’s specific backend, and has not been verified either way - treat this as unconfirmed, not as a solved RAM problem, and watch for collect() in step 6 doing more work than expected the first time you run it.

If RAM turns out to be a real problem in practice, one option short of a full comparator-arm deviation (below) is to take a random, representative sample of the background population instead of all of it - still much closer to SEPLINE’s “general population” cutpoints than a narrow comparator arm, at a fraction of the rows:

bef_population <- bef %>%
  filter(year %in% !!income_years) %>%
  select(pnr, year, familie_id, koen, foed_dag) %>%
  # a 500,000-person sample is still plenty for stable quintile cutpoints -
  # only do this if the full population turns out to be too much RAM
  slice_sample(n = 500000)

This is still a deviation from “the full general population” and should be reported as one, the same as a comparator arm - just a smaller one, and one that stays closer to what SEPLINE actually specifies.

Using a different reference population is a legitimate choice, but document it as a deviation. If you use a comparator arm from your own study instead of the full population (e.g. because eligibility criteria like “no prior surgery” or “≥5 years residency” make it a more relevant comparison for your specific outcome), say so explicitly - the mechanics below are identical, but the result is no longer SEPLINE’s “general population” cutpoints.

library(dplyr) # filter, select, left_join, group_by, summarise, mutate, bind_rows
library(lubridate) # year() to extract year from a date

# 1. The three calendar years SEPLINE asks for: the year before index, and
# the two years before that (Table 8, "Time of measurement") - never the
# index year itself, to avoid reverse causation
income_years <- unique(c(cohort$year_baseline, cohort$year_baseline - 1, cohort$year_baseline - 2))

# 2. Each cohort row needs its OWN 3-year window - not one window shared by
# the whole cohort (see "Before you extract anything" above: the same pnr can
# carry more than one baseline year). Build one row per (cohort row x year
# needed) first, so the years stay tied to the row they belong to:
cohort_income_years <- bind_rows(
  cohort %>% transmute(row_id, pnr, year = year_baseline), # baseline year
  cohort %>% transmute(row_id, pnr, year = year_baseline - 1), # 1 year before
  cohort %>% transmute(row_id, pnr, year = year_baseline - 2) # 2 years before
)

bef_3yr <- bef %>%
  semi_join(tibble(pnr = cohort$pnr), by = "pnr", copy = TRUE) %>% # only the cohort's pnr's, copy = TRUE: see AKM step 2
  filter(year %in% !!income_years) %>% # only years the cohort actually needs
  select(pnr, year, familie_id, koen, foed_dag) %>% # koen + foed_dag needed for the sex x age strata in step 8
  collect() # fetch into R

faik_3yr <- faik %>%
  filter(year %in% !!income_years) %>% # only years the cohort actually needs
  select(familie_id, year, famaekvivadisp_13) %>% # only the columns we use
  collect() # fetch into R

# 3. Attach each row's own 3 years of income, then average PER COHORT ROW -
# not per pnr, so a repeated pnr with two different baseline years gets two
# separate, correctly-windowed averages instead of one mixed-together number.
# Missing-year rule (Table 8, "Missing values"): 1 missing year -> mean of
# the other 2; 2 missing -> the 1 that exists; 0 available -> no value.
# na.rm = TRUE already does that arithmetic; n_years just records how many
# years it used, so you can see how much averaging happened per row.
income_mean <- cohort_income_years %>%
  left_join(bef_3yr, by = c("pnr", "year")) %>% # this row's household, for this specific year
  left_join(faik_3yr, by = c("familie_id", "year")) %>% # then that household's income, same year
  group_by(row_id) %>%
  summarise(
    n_years = sum(!is.na(famaekvivadisp_13)), # how many of the 3 years had a value
    mean_income = mean(famaekvivadisp_13, na.rm = TRUE), # mean disposable income over the years that exist
    .groups = "drop"
  ) %>%
  mutate(mean_income = if_else(n_years == 0L, NA_real_, mean_income)) # mean() of zero values is NaN, not NA - fix it

# 4. Negative income (Table 8, "Negative values"): possible, mostly for the
# self-employed. SEPLINE offers two options, not one fixed rule: exclude
# these individuals, or run the analysis twice - once counting them as low
# income, once as high income - as a sensitivity check. Decide which fits
# your study; do not silently drop or silently keep them.
income_mean %>%
  summarise(n_negative = sum(mean_income < 0, na.rm = TRUE), total = n())

# 5. Reference population for the cutpoints: same years, no pnr filter. This
# stays LAZY - no collect() here. income_years already spans every year any
# baseline year's 3-year window needs (step 1), so this is not a wider PULL
# than the cohort fetch above - but the population itself is all of Denmark,
# not just your cohort, so the filter/join/mean below are deliberately kept
# inside the database instead of materialised in R. filter(), left_join(),
# year(), floor() and mean() all translate to SQL and run there (verified
# against DuckDB); only the small per-stratum result in step 6 is collected.
# If bef and faik turn out to be on different underlying connections in your
# fastreg setup, this join will error asking for copy = TRUE - collect()
# each side first as a fallback, same as the single-year demo above.
bef_population <- bef %>%
  filter(year %in% !!income_years) %>% # same years, no pnr filter this time
  select(pnr, year, familie_id, koen, foed_dag) # koen + foed_dag for the sex x age strata

faik_population <- faik %>%
  filter(year %in% !!income_years) %>%
  select(familie_id, year, famaekvivadisp_13)

population_with_income <- bef_population %>%
  left_join(faik_population, by = c("familie_id", "year"))

# 6. Each population member's OWN 3-year average - the same rolling window
# as step 3, computed once per distinct baseline year the cohort actually
# uses (baseline_years), not per calendar year. A single-year population
# income would understate how stable most people's income is year to year,
# and would not be comparable to the cohort's own 3-year-averaged value - so
# this repeats step 3's exact logic for the population side instead of
# simplifying it away. The loop is over baseline_years (typically a handful
# of distinct years), not over every person - each pass filters
# population_with_income to that ref_year's 3 years and fixes age AT that
# ref_year (not year-by-year), so nobody's window splits across two
# age_group bands due to a birthday landing mid-window. collect() happens
# LAST in each pass, after the group_by/summarise(mean(...)) has already run
# inside the database - what reaches R per pass is one row per (person,
# stratum), not the raw multi-year population join.
baseline_years <- unique(cohort$year_baseline)

population_income <- lapply(baseline_years, function(by) {
  population_with_income %>%
    filter(year %in% !!c(by, by - 1, by - 2)) %>% # !! evaluates by LOCALLY first - see AKM step 2's index_year for why
    mutate(
      age = by - year(foed_dag), # age AT ref_year, fixed across the whole window
      age_group = floor(age / 5) * 5 # 5-year bands: 0, 5, 10, ...
    ) %>%
    group_by(pnr, koen, age_group) %>%
    summarise(mean_income = mean(famaekvivadisp_13, na.rm = TRUE), .groups = "drop") %>%
    collect() %>% # only the per-person summary leaves the database, not the raw rows
    mutate(ref_year = by)
}) %>%
  bind_rows()

# 7. Cutpoints: Q20/Q40/Q60/Q80 per sex x age group x year, from the
# reference population - these define what "low/medium/high income" means,
# independent of your own cohort's distribution
cutpoints <- population_income %>%
  group_by(koen, age_group, ref_year) %>%
  summarise(
    q20 = quantile(mean_income, 0.2, na.rm = TRUE),
    q40 = quantile(mean_income, 0.4, na.rm = TRUE),
    q60 = quantile(mean_income, 0.6, na.rm = TRUE),
    q80 = quantile(mean_income, 0.8, na.rm = TRUE),
    .groups = "drop"
  )

# 8. Classify the STUDY cohort against those cutpoints - not against its own
# ntile(), which would only compare people to each other. koen and foed_dag
# come from the same bef_3yr fetch as familie_id (step 2), taken at each
# row's own baseline year.
income_quintile <- cohort %>%
  select(row_id, pnr, year_baseline) %>%
  left_join(
    bef_3yr %>% select(pnr, year, koen, foed_dag),
    by = c("pnr", "year_baseline" = "year")
  ) %>%
  mutate(
    age = year_baseline - lubridate::year(foed_dag), # age reached in the baseline year
    age_group = floor(age / 5) * 5 # 5-year bands, matching step 6
  ) %>%
  left_join(income_mean, by = "row_id") %>%
  left_join(cutpoints, by = c("koen", "age_group", "year_baseline" = "ref_year")) %>%
  mutate(
    income_cat = case_when(
      is.na(mean_income) ~ "Unknown", # no income years available at all - see the NA-vs-Unknown callout above
      mean_income <= q20 ~ "Low", # quintile 1
      mean_income > q80 ~ "High", # quintile 5
      TRUE ~ "Medium" # quintiles 2-4 (Table 9's suggested 3-category grouping)
    )
  ) %>%
  select(row_id, mean_income, income_cat)

stopifnot(nrow(income_quintile) == nrow(cohort))

Two more things SEPLINE flags that this code does not handle for you. Inflation: income values should be adjusted to a common year before averaging across calendar years, using a consumer price index or GDP deflator (Table 8, Birth Cohort/Life Course Aspects) - not implemented here, since the right index depends on your study period. Continuous modelling: if you want income as a continuous variable instead of categories, SEPLINE warns that a linear term is biased (misclassification is worse at the low end, and the income-health relationship is not linear) and recommends splines or fractional polynomials instead.

cohort_ses <- cohort %>%

  left_join(cohort_udda %>% select(row_id, education_cat), by = "row_id") %>% # attach education
  left_join(income_quintile %>% select(row_id, income_cat), by = "row_id") # attach income quintile

# Sanity check: a correct join never changes the row count
stopifnot(nrow(cohort_ses) == nrow(cohort))
