Comorbidity

Baseline conditions as covariates: individual diagnoses or a combined measure, from LPR, LMDB or both

Comorbidity as a covariate in Danish register studies: individual diagnoses or a combined measure, defined from LPR diagnoses, LMDB prescriptions or both.
Last modified

November 24, 2026

Use this page when your analysis plan has comorbidity at baseline as a covariate. It helps you decide between adjusting for individual conditions and adjusting for one combined measure, and whether to define a condition from hospital diagnoses, dispensed prescriptions or both. It then shows the extraction of diagnoses before index. It builds on Extract from LPR and Medication (ATC), and you end with one 0/1 flag per condition per person, saved as .rds.

Individual conditions or one combined measure?

Which comorbidities to adjust for belongs to your analysis plan and typically follows from your DAG (directed acyclic graph, see Phase 1 - Choose your covariates using a DAG). There are two approaches:

  1. Individual comorbidities as separate covariates, for example the specific diagnoses you identified as confounders in your DAG. You extract these as ordinary diagnosis variables, with the same LPR pattern as on Outcomes. This gives the most control and transparency, but you have to know in advance which conditions are confounders.
  2. One combined measure of comorbidity burden: a count or an index built from hospital diagnoses, sometimes together with prescriptions. It is practical when many conditions are potential confounders, or when you want to describe the burden in Table 1. The Charlson Comorbidity Index is one such index; the code to compute it from LPR diagnoses is under Charlson Comorbidity Index below.

The Nordic Multimorbidity Index (NMI) was developed to predict mortality; use it with care as a measure of comorbidity burden. Its authors describe it as a multimorbidity measure that can be used as a confounder summary score, but its predictors and weights were chosen to predict 5-year mortality. This guide therefore uses it for mortality risk and not as the combined measure in approach 2. See NMI for the reasons.

With either approach, your own outcome must not be part of what you adjust for. If the outcome, or a strong predictor of it, is one of the conditions a combined measure counts, you partly adjust for the outcome itself. Check the list of conditions behind any index before you use it.

Diagnoses, prescriptions, or both?

Whether a condition is defined from hospital diagnoses, from dispensed prescriptions, or from both is a design decision you make per condition, and it changes who counts as having it.

Some conditions are captured well by LPR (the National Patient Register) on its own: the ones that reliably bring people to hospital, such as myocardial infarction or hip fracture. Others are mostly treated outside hospital. Hypertension is an example: people managed entirely in general practice never appear in LPR with an I10 diagnosis, but they do collect antihypertensives and so appear in LMDB, the prescription register.

Both single-source definitions fail, in opposite directions:

  • Diagnoses only miss everyone treated outside hospital: they look healthy.
  • Prescriptions only catch everyone on the drug, including those taking it for something else. Antihypertensives are also prescribed for heart failure and angina, so a definition of hypertension from ATC (Anatomical Therapeutic Chemical) codes alone over-counts.

If you combine the two, the halves normally need different rules:

Diagnoses (ICD-10, from LPR) Medication (ATC, from LMDB)
Typical window ever, or a lookback before index a recent window, e.g. the last year
How many events count one recorded diagnosis usually more than one dispensing
Onset date first qualifying contact date the dispensing rule is first met

A single dispensing is weak evidence of treatment, because some people fill a prescription once and stop. The pattern for “at least N dispensings within a window” is on Medication.

Whichever you choose, write the definition into your methods. Two studies that define hypertension differently are not measuring the same variable.

Extract diagnoses before index for your cohort

Filter LPR to your cohort and to the time before index, then reduce to one row per person per condition. The code below keeps everything on or before the index date; add a lower limit if your definition uses a fixed lookback. read_register() assumes fastreg is pointed at your registers.

library(fastreg) # read_register(), used inside get_lpr_diagnoses()
library(dplyr) # %>%, inner_join(), filter()

cohort <- readRDS("path/to/full_cohort.rds") # pnr + index_date

# lpr_diag has no pnr - pnr and contact date live in lpr_adm (join key recnum).
# get_lpr_diagnoses() from Extract from LPR does that join and keeps ONLY your cohort.
diagnoses_before_index <- get_lpr_diagnoses(unique(cohort$pnr)) %>%
  inner_join(cohort %>% select(pnr, index_date), by = "pnr") %>%
  filter(date_contact <= index_date) # on or before index = baseline

Turning that event log into one 0/1 flag per condition per person is the any() pattern in Extract from LPR - from event log to one row per person. For a condition that also has a prescription half, flag users as on Medication and combine the two per person. Save the result as .rds and link it in Phase 12.

Charlson Comorbidity Index from LPR

Two packages on DST compute the Charlson Comorbidity Index from LPR diagnoses: heaven::charlsonIndex() and EpiForsk::charlson_score() (see Algorithms & special packages). The example below uses charlson_score(). You extract the lookback yourself (often 5 years before the index date) and give the function every diagnosis in that window, not a code list: the function matches the codes to Charlson categories itself. Which diagnosis types to include is your choice; the example keeps types A, B and G (see Understand LPR for what each type means). The D-prefix (DG30 etc.) is handled by EpiForsk and does not need to be stripped first.

The lookback reads LPR2 (somatic and psychiatric) and LPR3, because LPR2 ends in March 2019 and an index date after that would otherwise miss most diagnoses. The LPR3 tables are filtered with lprindberetningssystem == "LPR3" as on Extract from LPR; read the warning about that filter before you use it. The window here runs up to, but not including, the index date; the general pattern above keeps the index date itself. Pick one and use it for every covariate.

library(fastreg)  # read_register()
library(dplyr)
library(EpiForsk) # charlson_score()

# Open the registers, as in get_lpr_diagnoses() on Extract from LPR
lpr_adm   <- read_register("lpr_adm")   %>% rename_with(tolower)   # LPR2 somatic contacts
lpr_diag  <- read_register("lpr_diag")  %>% rename_with(tolower)   # LPR2 somatic diagnoses
# any_of() renames the psychiatric keys only if your delivery renamed them
psyk_adm  <- read_register("t_psyk_adm")  %>% rename_with(tolower) %>%
  rename(any_of(c(pnr = "v_cpr", recnum = "k_recnum")))            # LPR2 psychiatric contacts
psyk_diag <- read_register("t_psyk_diag") %>% rename_with(tolower) %>%
  rename(any_of(c(recnum = "v_recnum")))                             # LPR2 psychiatric diagnoses
lpr3_k    <- read_register("lpr_a_kontakt")  %>% rename_with(tolower) %>%
  filter(lprindberetningssystem == "LPR3")   # read the warning linked above first
lpr3_d    <- read_register("lpr_a_diagnose") %>% rename_with(tolower) %>%
  filter(lprindberetningssystem == "LPR3")   # same filter as the contact table

# One row per (pnr, index_date), with each person's own 5-year lookback
# window already attached - this table is the size of your cohort, not the
# register. If your cohort has repeated pnr (e.g. matched with replacement),
# each occurrence gets its own row and its own window here. The window runs
# from window_start up to, but not including, window_end (the index date).
lookback_keys <- cohort %>%
  select(pnr, index_date) %>%
  mutate(window_start = index_date - 1825,   # 5 years = 1825 days, as on the NMI page
         window_end   = index_date)

# LPR3's contact time is a datetime, so its windows must be datetimes too:
# comparing a datetime with a date on a lazy table can silently go wrong
# (DST pitfall 4).
lookback_keys_dt <- lookback_keys %>%
  mutate(window_start = as.POSIXct(window_start, tz = "UTC"),
         window_end   = as.POSIXct(window_end, tz = "UTC"))

# The same steps for each source. contacts needs the columns pnr, key and
# date_contact, and diagnoses the columns key and c_diag.
window_dx <- function(contacts, diagnoses, keys) {
  contacts %>%
    # Coarse filter first (cheap): narrow to the union of every window in the
    # cohort, before the join - !! injects a single computed value, not a column
    filter(date_contact >= !!min(keys$window_start)) %>%
    # copy = TRUE sends the small keys table into the database, so the join
    # runs there, not in R. This matters more here than almost anywhere else
    # in the guide: Charlson needs EVERY A/B/G diagnosis in the window, not a
    # filtered-down code list, so the unjoined, unwindowed data for a whole
    # cohort can be large. Collecting it all into R first and only then
    # joining to the cohort and filtering by index_date can pull tens of GB
    # into RAM and crash the R session.
    inner_join(keys, by = "pnr", copy = TRUE) %>%
    # Precise filter (correctness): each row against its OWN window, not the global one
    filter(date_contact >= window_start, date_contact < window_end) %>%
    inner_join(diagnoses, by = "key") %>%
    select(pnr, index_date, date_contact, c_diag) %>%
    collect()
}

types <- c("A", "B", "G")   # A/B/G: all codes of these types, no ICD filter (G is LPR2 only)

lookback <- bind_rows(
  # LPR2 somatic
  window_dx(
    lpr_adm  %>% select(pnr, key = recnum, date_contact = d_inddto),
    lpr_diag %>% filter(c_diagtype %in% !!types) %>% select(key = recnum, c_diag),
    lookback_keys
  ),
  # LPR2 psychiatric
  window_dx(
    psyk_adm  %>% select(pnr, key = recnum, date_contact = d_inddto),
    psyk_diag %>% filter(c_diagtype %in% !!types) %>% select(key = recnum, c_diag),
    lookback_keys
  ),
  # LPR3, with datetime windows; diagnoses later disproved are left out
  window_dx(
    lpr3_k %>% select(pnr, key = dw_ek_kontakt, date_contact = kont_starttidspunkt),
    lpr3_d %>%
      filter(diag_kode_type %in% !!types,
             is.na(senere_afkraeftet) | senere_afkraeftet != "Ja") %>%
      select(key = dw_ek_kontakt, c_diag = diag_kode),
    lookback_keys_dt
  ) %>%
    mutate(date_contact = as.Date(date_contact))   # datetime -> date, now in R
)

charlson <- charlson_score(data = lookback, Person_ID = pnr, diagnosis_variable = c_diag)

Person_ID = pnr alone is not enough if your cohort has repeated pnr. lookback above is correctly windowed per (pnr, index_date), but charlson_score() itself only groups by the single Person_ID column you give it - it has no way to know about index_date. For a comparison cohort matched with replacement, that means diagnoses from all of a person’s index_date windows get pooled into one Charlson score, silently reattached to every occurrence of their pnr. If this applies to you, build a single combined key first (e.g. mutate(pnr_index = paste(pnr, index_date))) and pass Person_ID = pnr_index instead, then split the two columns back apart from the result afterwards.

regmorbidity: many conditions from editable code lists

regmorbidity is an R package in development for deriving many conditions at once from Danish register data. It is on GitHub only (not on CRAN), and parts of it have not been run on DST yet: read the package README for what has been tested before you rely on it. It computes no score and does not implement a published index. If you have code lists to contribute, get in touch.

How the package is designed, if you are writing your own code
  • Conditions live in plain CSV code lists, not in R code. One row per code, with columns for the condition, the vocabulary (ICD10 or ATC), the code and, for medication, the minimum number of dispensings and the window in days. One condition can therefore mix diagnoses and prescriptions, and the definitions can be edited and version-controlled without touching the code that runs them.
  • Medication conditions take a configurable count and window, and the onset date is the date of the qualifying dispensing.
  • Results are written to disk one file per condition, so a long run over the full register can resume after an interruption.
  • The bundled code lists take Prior et al. (2016) (doi:10.1093/aje/kwv324) as their starting point. They are meant to be revised for your own study and are not an implementation of that paper’s index.
